## 1. What the app does

A user registers, signs in, uploads one or more scanned or digital documents, and the app reads every page like a person would. It works out what kind of document each one is and extracts every detail that is actually written on the page, with no fixed list of fields for any document type. The user reviews each file next to the original page, edits, adds or removes details, and saves. The app learns from those corrections. The user can download the results.

## ZERO DEFAULTS (most important rule)

The app must never contain or display any default, built-in, placeholder or assumed field, column, label, value, caption, confidence number or status. An earlier version always showed fixed columns on every table, and that must never happen again.

- The only things shown on screen are things read from the user's own files, and the labels exactly as the page wrote them.
- Table columns are created at the moment of display, only from the labels found in that group's files. If a group's files have no value for a label, there is no empty "default" column for it.
- The code must contain no list, enum, schema, template, constant, translation file or database column that names specific document details (for example a model with fixed columns for names, dates, totals or parties). Details are stored generically as rows of label and value.
- Before you report anything, search the whole code base (front end, back end, database, tests, seed scripts, mock files) for hard-coded field names, sample data, fallback values such as "N/A", "Unknown", "—" used as a stored value, and fixed confidence or caption strings. Remove every one and list what you removed with file and line number. A "—" may only be drawn on screen for a missing cell, never stored.
- If a page has only one detail, the app shows one detail. If it has none, the file shows Failed with the reason "No details found on the page". An empty page must never look like a successful extraction.
- Test it: upload a page that contains a single line of text. Only that one detail may appear, with no other fields, columns or captions.

## 2. Tech stack

Use what the project already has wherever it works (see section 0). The list below is what to use for any part the project does not have, or that cannot do the job.

- Front end: React + TypeScript + Vite. Plain CSS using the same variables as `demo.html`. No UI framework that changes the look.
- Back end: Python 3.11+, FastAPI, SQLAlchemy, SQLite (file database). Background worker thread or task queue for reading files.
- Reading the pages:
  - Render each PDF page to an image (PyMuPDF), and accept PNG and JPG too.
  - Clean the image first: straighten crooked pages and remove speckle noise (OpenCV).
  - A vision-capable AI model reads the cleaned page image and returns the document type and every label and value it finds, with a confidence for each. Use the Claude API (model name in an environment variable, default `claude-sonnet-5-5`). The API key comes from an environment variable `ANTHROPIC_API_KEY`. Never put a key in code.
  - A second, independent check with Tesseract OCR on the same image. A value's confidence must come from how well the vision reading agrees with the Tesseract text and from the model's own confidence. Never a fixed number.
  - If the key is missing or the model call fails, the file shows Failed with the real reason. Never fall back to made-up or default values.
- Auth: email and password, passwords hashed with bcrypt, sessions with JWT or secure cookies.

## 3. The workflow (must match the demo)

1. **Sign in / Register.** The first screen is Sign in with a link to Register (name, email, password). After registering, the user is sent back to Sign in with a "Registered. Now sign in." message. No default or hard-coded account exists anywhere. Every other screen and every API call requires a signed-in user. Sign out returns to Sign in. Each user sees only their own files.
2. **Upload.** The user picks one or more files (drag and drop or file picker). Show the same rules list as the demo.
3. **Reading.** The user sees each file's real stage (Waiting, Reading, Extracting, Done, Failed) and overall progress ("3 of 6 files finished", with a percentage). Progress comes from the back end (poll every second or use server-sent events). A file is Done only if at least one detail was extracted from its page. If nothing was found or reading failed, it is Failed and shows the real reason.
4. **Results.** Files are grouped by the document type the app found. Each group's table shows only the details found in that group's documents (union of the labels in that group). A cell with no value shows "—". There are no default columns. Status shows Done, "Done, check" (when any value has confidence below 85%), or Failed with the reason. The batch summary and each row use the same status from the same data. A View link opens each file.
5. **View (check and edit).** Original page on the left, large enough to read, with the page condition detected from the image (clean, slightly skewed, speckled, and so on). Details on the right, each with its own real confidence. The user can edit a name or value, add a missing detail, remove a wrong one, and press Save. Saving writes all changes to the database. After a refresh, a new sign-in or a server restart the saved values are still there and are never overwritten by the original reading. Edited and added details are marked. Previous and Next move between files ("2 of 6"). Back returns to the results.
6. **Learning.** Every saved correction is stored (document type, label, original value, corrected value, a short description of the page layout). When reading a new document of a similar type or layout, include the most relevant stored corrections as examples in the model's instructions, so the same mistakes are not repeated. Show "Learned from N corrections" on the Results screen when N is more than zero.
7. **Download.** "Download all as ZIP" gives a ZIP with the original files, a CSV and an Excel file of the results (one sheet per document type, columns are the labels found). Values in the downloads are the saved (edited) values.
8. **Past batches.** The Upload screen lists the user's earlier batches with a link to reopen them.

## 5. Back end design

Database tables (names can vary): `users`, `batches` (id, user_id, name, created_at), `files` (id, batch_id, original_name, stored_path, sha256, status, stage, error, doc_type, page_condition, started_at, finished_at), `fields` (id, file_id, label, value, original_value, confidence, source ["read" | "edited" | "added"], position), `corrections` (id, user_id, doc_type, label, original_value, corrected_value, layout_hint, created_at).

API (all except register and login need auth):
- `POST /api/register`, `POST /api/login`, `POST /api/logout`, `GET /api/me`
- `POST /api/batches` (multipart upload of many files; returns batch id and starts background reading)
- `GET /api/batches`, `GET /api/batches/{id}` (status of every file, stage, overall progress, groups)
- `GET /api/files/{id}` (fields, doc type, page condition, original page image URL)
- `PUT /api/files/{id}/fields` (the complete list after the user's edits; saves and records corrections)
- `GET /api/files/{id}/page/{n}` (page image)
- `GET /api/batches/{id}/download` (ZIP)

Reading pipeline per file, run in the background: store file → render pages → clean image → detect page condition → vision extraction (type, labels, values, confidence) → Tesseract cross-check → combine confidence → save → set status. Update `stage` at every step so the front end can show the real progress. Catch every error and store its real message.
